# 功能规格：语义资产基础与素材理解

**功能分支**：`codex/phase-0-discovery`  
**创建日期**：2026-08-24  
**状态**：规划中  
**输入**：重写 Phase 2，使文件资产、角色、服装、道具、角色状态与后续 AI 分镜选材形成可追踪的数据链。

## 澄清记录

### 2026-08-24

- Q：角色、服装、道具是否只是一个 Asset 下的不同状态？ → A：不是。Character 是稳定身份；
  Outfit、Prop 等是可独立复用的 ProductionAsset；CharacterStateVersion 只组合角色在某一造型
  状态下的 Outfit、Hair、Makeup、Accessory。
- Q：这些数据写入哪里？ → A：PostgreSQL 保存元数据、版本、关系、审核和来源；本地
  StorageProvider 保存原始二进制；凭证只存在环境变量或系统密钥设施中。
- Q：AI 分镜自动筛选符合 Character 的资产是否考虑？ → A：Phase 2 提供结构化需求合同、
  确定性硬过滤和候选预览；Phase 3 再持久化 Shot 绑定和最终 AssetResolutionManifest。
- Q：是否参考资产表设计评估？ → A：本规格采用该评估提出的文件层、语义层、角色状态层、
  分镜绑定层分离方案，并把发现的 Phase 1 加固项列为 Phase 2A 的入口门槛。

## 背景与目标

Phase 1 已能把用户导入的文件保存为项目内素材，但“一个文件”不等于“一个可复用的制作资产”。
例如，同一角色可能有多个造型版本和多个状态；服装、道具、场景、声音和 LoRA 也应独立存在并
可复用。后续 AI 分镜还需要按“指定角色 + 指定状态 + 参考用途”等硬条件筛选素材，而不是
在文件名或非结构化标签中猜测。

Phase 2 因此分为两个连续交付：

- **Phase 2A：资产底座与语义资产**——加固 Phase 1 文件导入，建立 ProductionAsset、版本、
  角色状态、组件关系，以及语义版本到原始文件的用途绑定。
- **Phase 2B：素材理解与人工审核**——以零调用预览为默认，通过受控分析帮助填写候选事实；
  机器结果必须经用户接受或修正后，才能参与后续确定性选材。

本阶段为 AI 分镜定义可消费的资产候选合同和筛选预览，但不实现 Storyboard、Shot、正式
AssetResolutionManifest、视频生成或自动创意决策。

## 用户场景与独立验收

### 用户故事 1——获得可信、可审计的文件资产（优先级：P1）

作为项目所有者，我需要确认每个导入文件的内容、校验状态和导入结果可信，这样后续语义资产
与 AI 分析不会建立在损坏、错配或未经验证的文件上。

**优先原因**：语义资产、素材理解和分镜选材都依赖可信原件；该层错误会污染全部下游结果。

**独立验收**：导入正常、截断、伪装格式、重复哈希和批次内局部失败的素材；系统逐项保存
结果，已有目标文件必须重新计算哈希，损坏文件不会成为 READY，任何拒绝均有审计记录。

**验收场景**：

1. **假如** 内容寻址路径已存在同尺寸文件，**当** 再次导入相同声明哈希的素材，**那么**
   系统必须重新计算现有文件哈希，只在字节一致时复用。
2. **假如** 文件只有合法签名但媒体结构损坏或截断，**当** 导入完成，**那么** 原件仍可被
   保留为证据，但状态不得为 READY，并记录可理解的失败原因。
3. **假如** 同一批次含成功项与失败项，**当** 其中一个项目失败，**那么** 其他项目仍独立
   完成，每一个请求项都有且仅有一个终态导入尝试记录。
4. **假如** 用户浏览大型素材库，**当** 搜索或翻页，**那么** 结果稳定、有总数，并且不会
   因一次性加载全部记录而失去响应。

---

### 用户故事 2——建立可复用、可版本化的制作资产（优先级：P1）

作为项目所有者，我希望把文件组织成角色、服装、道具、场景、声音、LoRA 等稳定资产，并
保留版本历史，从而让业务身份不依赖某个文件或某次分析结果。

**优先原因**：这是连接素材文件、角色状态、分镜需求与生成输入的核心语义层。

**独立验收**：创建不同类型的 ProductionAsset；为其新增草稿版本、关联来源文件、激活一个
版本并停用旧版本；系统保留历史版本和来源，不覆盖已激活记录。

**验收场景**：

1. **假如** 用户有三张同一件外套的照片，**当** 创建 OUTFIT 资产版本并绑定这些照片，
   **那么** 三个文件属于同一个语义版本，但各自仍保留独立文件身份与来源。
2. **假如** 一个角色换了新版设定，**当** 用户发布新 CharacterVersion，**那么** 原版本仍
   可追溯，默认解析只使用当前允许的版本。
3. **假如** 用户尝试跨项目关联文件或组件，**当** 保存关系，**那么** 系统拒绝该操作且不
   产生部分关系。
4. **假如** 资产被停用，**当** 请求未来分镜候选，**那么** 它不会进入合格候选，但历史引用
   仍可读取。

---

### 用户故事 3——表达角色版本和可复用状态（优先级：P1）

作为项目所有者，我希望一个 Character 有稳定身份、多个版本和多个状态；每个状态能够指定
服装、发型、妆容和配饰，从而准确表达“这个角色在这个镜头中的样子”。

**优先原因**：角色连续性是分镜和生成最重要的资产约束之一，不能用文件标签替代。

**独立验收**：为同一角色创建两个版本和多个 CharacterStateVersion；把独立 OUTFIT、HAIR、
MAKEUP、ACCESSORY 资产版本绑定为状态组件；锁定发布后创建新修订而不是原地改写。

**验收场景**：

1. **假如** 角色“Lala”有日常装和晚宴装，**当** 用户建立两个状态，**那么** 它们共享同一
   Character 身份，但可绑定不同服装、发型、妆容和配饰版本。
2. **假如** 普通手持道具“雨伞”只在某个镜头出现，**当** 编辑角色状态，**那么** 系统不会
   要求把它固化到角色状态；它应留给 Phase 3 的 Shot 级绑定。
3. **假如** 某件配饰是角色状态的固有组成，**当** 将其绑定为 ACCESSORY 组件，**那么**
   后续候选解析必须能识别该状态所要求的组件版本。
4. **假如** 已发布状态被修改，**当** 用户保存，**那么** 系统创建新状态版本，旧状态及其
   组件关系保持不变。

---

### 用户故事 4——为 AI 分镜准备可解释的素材候选（优先级：P2）

作为项目所有者，我希望说明每个文件如何服务某个资产版本，并预览后续 AI 分镜按硬条件能够
得到哪些候选，这样可以在进入分镜前补齐缺失素材。

**优先原因**：它验证 Phase 2 的数据是否真的支持自动选材，同时把“候选筛选”与“AI 创意
判断”分开。

**独立验收**：为资产版本绑定不同 ReferenceUsage、Viewpoint、ShotScale 的文件；提交一个
不创建分镜的结构化候选请求；系统只返回同项目、指定角色/状态、READY 且已批准的合格候选，
并给出纳入或排除原因。

**验收场景**：

1. **假如** 分镜需求指定 Lala 的晚宴装状态和全身参考，**当** 预览候选，**那么** 系统先按
   项目、角色、状态、用途和就绪状态做确定性筛选，不把其他角色的高相似图片混入。
2. **假如** 只有脸部参考而缺少所需全身参考，**当** 预览候选，**那么** 系统失败关闭并返回
   可操作的缺口，不静默放宽条件。
3. **假如** 文件属于正确角色但绑定到旧的停用版本，**当** 未明确锁定历史版本，**那么**
   它被排除并显示原因。
4. **假如** 所有硬条件通过，**当** 候选多于一个，**那么** 系统可按可解释的结构化质量事实
   排序，但本阶段不替用户作正式 Shot 选择。

---

### 用户故事 5——受控理解素材并由用户确认（优先级：P2）

作为项目所有者，我希望主动选择素材进行分析，审核机器建议并修正后再用于语义资产，这样能
减少人工录入，同时不会把模型猜测当成事实。

**优先原因**：素材理解能提高建档效率，但必须建立在 Phase 2A 的稳定身份与审核边界上。

**独立验收**：在没有凭证和 Worker 的情况下预览分析清单，外部调用数为零；使用 Fake
Provider 完成一次受控运行；接受、拒绝和修正建议后，机器原始修订不变，只有批准投影可以
更新语义绑定或参与候选筛选。

**验收场景**：

1. **假如** 用户只打开页面、导入文件或预览分析，**当** 没有明确确认 LIVE，**那么** 外部
   Provider 调用数始终为零。
2. **假如** 用户确认精确清单，**当** Worker 执行，**那么** 一份授权最多产生一次 Provider
   Attempt；超时、崩溃或不明结果不会自动重试或切换 Provider。
3. **假如** Provider 返回角色、用途、视角或质量建议，**当** 尚未人工接受，**那么** 建议
   不得成为正式语义事实或合格选材依据。
4. **假如** 用户修正机器建议，**当** 保存修正，**那么** 系统追加所有者修订和审核决定，
   不覆盖机器输出，并能追溯是谁、何时、基于哪次运行完成修正。

## 边界情况

- 同一文件可以服务同一语义版本的多个参考用途，但不得产生重复的等价绑定。
- 同一 StoredObject 可以被同一项目中的多个 ProjectAsset 引用；删除业务引用不得立即删除
  内容寻址原件。
- 无法完整探测的文件必须保留原件和失败证据，但不能被标记为可供分析或生成使用。
- 历史版本、状态或文件被停用后，已有审计引用仍需可读；新候选查询默认排除它们。
- 一个文件可能同时包含多名角色；未经用户拆分或确认，不得自动绑定到某个单一 Character。
- 机器结果包含未知类型、越界文本、重复槽位、缺失槽位或未请求素材时，整次运行失败且不
  写入部分批准事实。
- Provider 技术成功不代表内容正确；人工接受也不代表生成质量已批准。
- 并发发布两个资产版本或状态版本时，只能有一个成为当前活动版本，失败方不得覆盖成功方。

## 功能需求

### Phase 2A：文件资产加固

- **FR-001**：系统必须把现有文件层实体在领域和 API 中明确为 ProjectAsset，同时保持现有
  数据和外部引用可迁移；不得把它误当成 Character、Outfit 等语义资产。
- **FR-002**：内容寻址目标已存在时，系统必须重新计算目标文件 SHA-256 后再复用，不能只
  比较文件大小、扩展名或声明值。
- **FR-003**：系统必须区分 PRESERVED、READY、INVALID、REMOVED；只有通过结构探测和哈希
  复核的媒体才能进入 READY。
- **FR-004**：媒体探测结果必须作为 StoredObject 的追加式 MediaProbeResult 保存，包含
  探测器版本、时间、结构事实、错误分类和结果状态，不覆盖历史探测证据。
- **FR-005**：每次批量导入必须有 AssetImportBatch；每个请求项必须独立处理，并留下恰好
  一个终态 AssetImportAttempt，包括角色缺失、数量超限、格式错误和运行时失败。
- **FR-006**：导入尝试、项目活动、ProjectAsset 与 Project 的关系必须在数据库边界防止
  跨项目错配。
- **FR-007**：素材库必须支持稳定分页、总数、搜索和状态/媒体类型筛选。
- **FR-008**：现有 READY 数据迁移时必须先降为 PRESERVED，再由显式可重复验证流程晋升为
  READY 或 INVALID；不得凭旧状态推断结构有效。

### Phase 2A：语义资产、版本与角色状态

- **FR-009**：系统必须支持独立的 ProductionAsset，至少包含 CHARACTER、OUTFIT、PROP、
  SCENE、VOICE、LORA、HAIR、MAKEUP、ACCESSORY 和 OTHER 类型。
- **FR-010**：ProductionAsset 必须拥有项目内稳定身份、名称、类型、生命周期状态和追加式
  版本历史；版本状态至少包含 DRAFT、ACTIVE、RETIRED。
- **FR-011**：系统必须保证每个 ProductionAsset 同时至多一个默认 ACTIVE 版本，并允许调用
  方明确锁定历史版本以重现旧决定。
- **FR-012**：系统必须通过 AssetVersionFile 把 ProductionAssetVersion 与一个或多个
  ProjectAsset 绑定；绑定必须记录 ReferenceUsage，并可记录 Viewpoint、ShotScale、裁切和
  人工说明。
- **FR-013**：ReferenceUsage 至少必须表达 IDENTITY、FACE、FULL_BODY、OUTFIT_DETAIL、
  PROP_DETAIL、SCENE_STYLE、POSE、CONTROL 和 TRAINING_SOURCE；它不能与资产类型混为一谈。
- **FR-014**：系统必须支持 ProductionAssetRelation 表达可复用语义关系，并保存关系版本、
  来源与生命周期，而不是只在文本标签中隐含关系。
- **FR-015**：CHARACTER 类型必须拥有 CharacterProfile，并支持 CharacterVersion；角色稳定
  身份不得随某张图片、服装或状态变化。
- **FR-016**：系统必须支持 CharacterStateVersion，并通过 CharacterStateComponent 绑定
  OUTFIT、HAIR、MAKEUP、ACCESSORY 等独立资产版本。
- **FR-017**：已发布 ProductionAssetVersion、CharacterVersion 和 CharacterStateVersion
  不得原地改写；任何内容变化必须创建新版本并保留来源链。
- **FR-018**：普通镜头级手持或环境道具不得强制进入 CharacterState；本阶段必须为 Phase 3
  的 ShotAssetBinding 保留独立 PROP 资产身份。
- **FR-019**：所有语义关系必须项目隔离；跨项目文件、版本、状态或组件关联必须原子拒绝。

### Phase 2：确定性候选预览

- **FR-020**：系统必须定义版本化 AssetCandidateRequirement，至少能指定项目、资产类型、
  ProductionAsset/Character、CharacterStateVersion、ReferenceUsage、Viewpoint、ShotScale 和
  Provider 媒体约束。
- **FR-021**：候选服务必须先执行硬条件过滤：同项目、指定稳定身份/锁定版本、活动状态、
  READY 文件、已批准语义事实、参考用途和媒体能力；任何相关性排序不得绕过硬条件。
- **FR-022**：候选结果必须返回合格候选、结构化排序事实、排除原因和缺口；没有合格项时
  必须失败关闭，不静默跨角色、跨项目、换状态或降低用途要求。
- **FR-023**：本阶段的候选服务只能提供预览和合同验证，不得创建正式 Shot、替用户选定
  ProductionAssetVersion，或持久化 Phase 3 的 AssetResolutionManifest。
- **FR-024**：Phase 2 不要求向量数据库或 Embedding；未来 AI 排序只能在确定性硬过滤后的
  合格集合内进行，并须另行定义模型授权与审计。

### Phase 2B：素材理解和审核

- **FR-025**：系统必须允许用户选择 1–9 个同项目 READY 图片创建不可变分析预览；预览不得
  创建授权、运行、尝试或外部调用。
- **FR-026**：分析预览必须显示 Provider/模型、合同版本、匿名素材槽位、文件哈希、外发说明、
  最大调用数和过期时间，并生成规范化清单哈希。
- **FR-027**：LIVE 分析必须要求服务端 Gate 和持久化一次性授权；授权须绑定精确清单、
  Provider、模型、合同版本、目标素材和最大一次调用，并在网络尝试前消费。
- **FR-028**：重复确认、Worker 重投递、租约恢复、超时、崩溃和不明确 Provider 结果不得导致
  第二次自动尝试、自动回退、自动替换或授权返还。
- **FR-029**：素材理解必须通过 Provider 中立、版本化结构合同执行；Provider 输出必须覆盖
  每个请求槽位且不得增加未知槽位，非法结果整体失败，不写部分修订。
- **FR-030**：系统不得持久化图片副本、Base64、凭证、完整 Provider Payload 或未经验证的
  原始响应；日志不得包含本地路径、素材内容、用户修正文案或可能回显请求的原始错误。
- **FR-031**：每次分析必须追加保存 Manifest、Grant、Run、Attempt 和机器 Revision 的来源
  关系；Provider 技术完成不得自动成为批准事实。
- **FR-032**：接受、拒绝和修正必须追加保存 Review；修正创建 OWNER Revision，机器 Revision
  保持不可变。
- **FR-033**：只有当前有效且被接受的 Revision 才能进入 Approved Projection；把批准结果
  应用到语义资产或文件绑定时必须记录来源和幂等键，且不得静默覆盖人工数据。
- **FR-034**：真实 Provider 执行不属于 Phase 2 规划或默认实现验收；Fake Provider、合同测试
  和零调用账本必须足以验证完整流程。

## 关键实体

- **StoredObject**：按内容寻址保存的原始二进制身份，不包含业务语义。
- **ProjectAsset**：项目中的文件引用及其生命周期；对应 Phase 1 现有 Asset 的领域重命名。
- **MediaProbeResult**：对 StoredObject 的追加式结构探测证据。
- **AssetImportBatch / AssetImportAttempt**：批量请求与逐项终态审计。
- **ProductionAsset / ProductionAssetVersion**：稳定语义身份及其不可变版本。
- **AssetVersionFile**：语义版本与文件之间带用途、视角、景别的关系。
- **ProductionAssetRelation**：语义资产或版本之间的可追踪关系。
- **CharacterProfile / CharacterVersion**：角色稳定身份的专属信息与版本。
- **CharacterStateVersion / CharacterStateComponent**：角色在特定造型状态下的版本和组件绑定。
- **AssetCandidateRequirement / AssetCandidateResult**：Phase 3 可复用的确定性候选输入和解释性
  输出；本阶段不代表正式 Shot 决定。
- **AssetUnderstandingManifest / Grant / Run / Attempt / Revision / Review**：受控素材理解及人工
  审核的追加式证据链。

## 范围边界

### 本阶段包含

- Phase 1 文件资产的安全加固、状态迁移、媒体探测、批次审计和分页搜索。
- 语义资产、版本、角色状态、组件关系和文件用途绑定。
- 不产生外部调用的确定性候选预览与缺口提示。
- 图片素材理解的预览、一次性授权、Fake Provider 执行、历史和人工审核。
- Provider 中立合同与 OpenAI Adapter 代码路径；真实 LIVE 仍需之后单独确认。

### 本阶段不包含

- Storyboard、StoryboardVersion、Shot、ShotAssetBinding 或正式 AssetResolutionManifest。
- AI Director、Shot Planner、GenerationSpec、ComfyUI 提交、视频生成、QA 或成片装配。
- 自动选择或自动批准角色、状态、文件、模型输出或生成结果。
- Embedding、pgvector、相似度检索、自动 LoRA 训练、多人协作或多租户权限。
- 音视频语义理解；Phase 2B 首版只分析静态图片。

## 依赖与假设

- Phase 0.5 的视频路径证据和 Phase 1 的项目/文件存储保持不变。
- 本地单用户仍按项目进行逻辑隔离；“单用户”不等于允许跨项目关系。
- PostgreSQL 保存业务记录和来源关系，本地 StorageProvider 保存二进制；图片不进入数据库。
- 资产管理员拥有创建和审核权限；本阶段不设计复杂角色权限。
- Phase 3 将持久化 ShotAssetRequirement、ShotAssetBinding 和 AssetResolutionManifest，并消费
  本阶段冻结的候选合同。

## 成功标准

- **SC-001**：全部导入测试中，100% 请求项都有一个终态尝试记录；单项失败不影响同批其他项。
- **SC-002**：对已有同尺寸错误内容的碰撞测试，系统 100% 拒绝复用；损坏媒体 0% 进入 READY。
- **SC-003**：迁移后所有旧 READY 记录均进入 PRESERVED，并能通过可重复验证明确晋升为 READY
  或标记 INVALID，且原文件和历史活动不丢失。
- **SC-004**：用户能在不改动文件身份的情况下，为同一 Character 建立至少两个版本、两个
  状态，并分别复用独立 OUTFIT 和 ACCESSORY 版本。
- **SC-005**：跨项目关系、重复活动版本和已发布版本原地修改的合同/数据库测试全部被拒绝，
  且不产生部分写入。
- **SC-006**：给定固定资产 Fixture，候选服务 100% 可重复返回相同合格集合和排除理由；错误
  角色、状态、项目、用途或非 READY 文件 0% 进入合格集合。
- **SC-007**：缺少必要参考时，用户在候选预览中能看到明确缺口，系统不会生成正式选择或
  静默降级。
- **SC-008**：导入、浏览、预览候选和预览分析的外部调用数均为 0；无 LIVE 授权时任何路径
  都不能产生 Provider Attempt。
- **SC-009**：每个已确认 LIVE Run 最多一个 Attempt；重复提交、重投递、崩溃和超时测试中的
  自动重试与回退次数均为 0。
- **SC-010**：机器 Revision 在接受、拒绝和修正后字节级不变；Approved Projection 只返回
  当前有效的已接受内容。
- **SC-011**：500 个 ProjectAsset、100 个语义资产版本和 100 条理解修订下，素材库和候选
  预览的首个有用结果在目标本地环境中 2 秒内返回。
- **SC-012**：所有自动化验收可用 Fake Provider 与真实 PostgreSQL 完成；最终调用账本明确
  记录外部 Provider 调用总数为 0，除非用户之后另行批准一次真实执行。
